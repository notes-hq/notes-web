# Notes Web

Frontend-часть информационной системы заметок с тегами. Проект представляет собой React-приложение, которое взаимодействует с backend API, позволяет пользователю создавать, просматривать, редактировать, удалять, искать и фильтровать заметки.

## Демо

Рабочая версия проекта доступна по адресу:

```text
http://188.225.58.19/
```

Демо-стенд размещен на сервере и может быть временно недоступен. Для проверки проекта независимо от сервера используйте локальный запуск по инструкции ниже.

## Назначение проекта

`notes-web` является frontend-репозиторием системы заметок. Его основная задача - предоставить пользователю удобный web-интерфейс для работы с заметками и тегами, при этом не смешивая UI-логику с хранением данных.

Frontend не хранит заметки постоянно в браузере. Он работает как клиент backend API: отправляет запросы, отображает полученные данные, выполняет frontend-валидацию формы и управляет состояниями интерфейса.

## Место frontend в общей системе

Проект состоит из двух самостоятельных репозиториев, которые разрабатываются в рамках одного рабочего пространства:

- `notes-api` - backend API на Node.js, Express и MySQL;
- `notes-web` - frontend-приложение на React и Vite.

Такое разделение позволяет независимо развивать, тестировать и разворачивать каждую часть системы. Frontend является одним из возможных клиентов backend и взаимодействует с ним только через REST API. Благодаря этому backend можно использовать и для других клиентов: консольного приложения, desktop-приложения, мобильного приложения, Telegram-бота или другого web-интерфейса.

Согласованность frontend и backend обеспечивается через API-контракт. В backend этот контракт формализован в `openapi.yaml`, а во frontend базовый URL API задается через переменную окружения `VITE_API_BASE_URL`.

## Основные возможности интерфейса

Frontend реализует следующие возможности:

- просмотр списка заметок;
- отображение количества найденных заметок;
- создание новой заметки;
- редактирование существующей заметки;
- удаление заметки;
- подтверждение удаления через стандартный `confirm`;
- поиск по заголовку и тексту заметки;
- фильтрация по одному тегу;
- комбинированное применение поиска и фильтра;
- ручное применение фильтров по Enter или кнопке "Найти";
- сброс активных фильтров;
- отображение тегов в формате `#tag`;
- стабильная цветовая палитра тегов;
- отображение preview текста заметки;
- frontend-валидация обязательных полей;
- запрет ввода hashtag-токенов в основное поле текста;
- обработка сетевых и HTTP-ошибок;
- горячая клавиша `Ctrl+Enter` для сохранения формы;
- отдельные страницы списка, создания и редактирования;
- темная визуальная тема.

## Обоснование выбранного стека

Frontend реализован на следующем стеке:

- **React** - библиотека для построения компонентного пользовательского интерфейса;
- **React Router** - маршрутизация внутри single-page application;
- **Vite** - dev-сервер и сборщик frontend-приложения;
- **JavaScript ES Modules** - модульная организация кода;
- **CSS** - стилизация интерфейса без дополнительного UI-фреймворка.

React выбран из-за компонентного подхода и декларативного управления интерфейсом. В приложении есть несколько устойчивых UI-сущностей: форма заметки, карточка заметки, панель фильтров, верхнее меню и страницы. React позволяет разделить эти части на независимые компоненты и управлять ими через состояние.

Vite используется как современный инструмент разработки. Он обеспечивает быстрый dev-сервер, удобную сборку production-версии и минимальную конфигурацию. Для проекта такого масштаба это позволяет сосредоточиться на логике приложения, не перегружая структуру сложной настройкой сборки.

React Router используется для разделения приложения на страницы без полной перезагрузки браузера. В проекте есть три основных маршрута: список заметок, создание заметки и редактирование заметки.

## Почему React + Vite

Выбор React и Vite обусловлен несколькими факторами:

- **Компонентность.** Повторяющиеся элементы интерфейса вынесены в отдельные компоненты, что упрощает чтение и поддержку кода.
- **Декларативное отображение состояния.** Интерфейс зависит от состояния приложения: загрузка, ошибки, пустой список, активные фильтры, процесс сохранения или удаления.
- **SPA-маршрутизация.** Пользователь переходит между страницами без полной перезагрузки приложения.
- **Минимальная конфигурация.** Vite дает быстрый старт и не требует сложной ручной настройки.
- **Переносимость навыков.** React, маршрутизация, API-слой и компонентная архитектура являются распространенными практиками современной frontend-разработки.

При этом проект не использует глобальные state-management библиотеки вроде Redux, Zustand или MobX, так как для текущего объема достаточно локального состояния страниц и компонентов.

## Архитектура frontend

Frontend построен по модульному принципу:

```text
React app
  -> pages
  -> components
  -> api
  -> utils
  -> backend REST API
```

Основные слои:

- `pages` - страницы приложения и сценарии работы пользователя;
- `components` - переиспользуемые UI-компоненты;
- `api` - функции для обращения к backend;
- `utils` - функции нормализации тегов, формирования payload, preview и форматирования даты;
- `styles` - стили интерфейса.

Такое разделение позволяет не смешивать разные типы логики. Например, `NoteForm` отвечает за отображение формы, но не знает, создает страница заметку или редактирует ее. API-запросы вынесены в `notesApi.js`, а правила работы с тегами - в `utils/notes.js`.

## Маршруты приложения

| Маршрут | Назначение |
|---|---|
| `/` | Список заметок, поиск, фильтр по тегу, удаление |
| `/create` | Создание новой заметки |
| `/edit/:id` | Редактирование и удаление конкретной заметки |
| `*` | Перенаправление на `/` |

На маршруте `/edit/:id` пункт меню "Все заметки" остается активным, потому что редактирование относится к контексту списка заметок.

## Взаимодействие с backend

Frontend взаимодействует с backend только через REST API. Базовый URL задается переменной окружения:

```env
VITE_API_BASE_URL=http://localhost:3000/api/v1
```

Для production-сборки в этом проекте используется файл `.env.production`:

```env
VITE_API_BASE_URL=/api/v1
```

Такой вариант рассчитан на reverse proxy: браузер обращается к `/api/v1` на том же домене, с которого открыт frontend, а nginx проксирует эти запросы к backend.

В коде frontend не зашивается конкретная версия API. Компоненты и страницы вызывают функции API-слоя, а API-слой добавляет ресурсные пути:

```text
/notes
/notes/:id
```

Такой подход позволяет переключить frontend на другой backend URL или новую версию API через конфигурацию окружения, не изменяя исходный код компонентов.

## API-слой

Файл `src/api/notesApi.js` отвечает за все обращения к backend.

Он реализует:

- построение полного URL;
- добавление query-параметров;
- исключение пустых query-параметров;
- отправку `GET`, `POST`, `PATCH`, `DELETE`;
- обработку `204 No Content` без вызова `response.json()`;
- чтение backend-ошибки в формате `{ message }`;
- оборачивание сетевых ошибок в `ApiError`;
- сохранение HTTP-статуса ошибки.

Страницы не вызывают `fetch` напрямую. Это снижает дублирование и делает обработку API-ответов единообразной.

## Работа с формой заметки

Форма заметки разделяет пользовательский ввод на три поля:

- `title` - заголовок;
- `noteText` - основной текст заметки;
- `tagsInput` - отдельное поле тегов.

Backend принимает только `title` и `content`, поэтому frontend перед отправкой собирает итоговый payload:

```json
{
  "title": "Изучить backend",
  "content": "Разобрать Express и MySQL\n#study #backend"
}
```

Теги добавляются в `content` отдельной последней строкой. Это позволяет backend извлекать теги из единого текстового поля, а frontend - предоставлять пользователю более удобный интерфейс с отдельным полем тегов.

## Работа с тегами

Пользователь может вводить теги через запятую или пробел:

```text
study, backend
```

или:

```text
study backend
```

Frontend нормализует ввод:

- убирает начальный `#`, если пользователь его ввел;
- приводит имя тега к lowercase;
- удаляет пустые значения;
- удаляет дубликаты;
- сохраняет порядок первого появления.

В интерфейсе теги отображаются явно с символом `#`:

```text
#study
#backend
```

## Обратная раскладка заметки при редактировании

При загрузке заметки с backend frontend получает `content` и `tags`. Для страницы редактирования нужно снова разложить данные на:

- основной текст заметки;
- поле тегов.

Служебная строка тегов удаляется из текста только при уверенном совпадении:

1. строка является последней непустой строкой `content`;
2. строка состоит только из hashtag-токенов;
3. после нормализации эти токены совпадают с массивом `note.tags`.

Если совпадения нет, frontend не пытается агрессивно угадывать структуру `content` и показывает текст как есть. Это важно для заметок, которые могли быть созданы не текущим frontend, а другим клиентом или прямым API-запросом.

## Поиск и фильтрация

Поиск и фильтрация применяются вручную:

- по нажатию Enter в поле поиска или тега;
- по кнопке "Найти".

Поиск не запускается на каждое нажатие клавиши. Это сознательно упрощает поведение интерфейса и снижает количество запросов к backend.

Фильтр по тегу поддерживает один тег. Значение фильтра нормализуется:

- очищается через `trim`;
- начальный `#` удаляется;
- значение приводится к lowercase.

Если поиск и тег указаны одновременно, frontend отправляет оба параметра, а backend применяет комбинированный фильтр.

## Создание заметки

На странице `/create` пользователь заполняет форму и сохраняет заметку.

Перед отправкой frontend:

1. Проверяет, что заголовок не пустой.
2. Проверяет, что текст заметки не пустой.
3. Проверяет, что пользователь не ввел hashtag-токены в основное поле текста.
4. Нормализует теги из поля `tagsInput`.
5. Формирует `content`.
6. Отправляет `POST /notes`.

После успешного создания пользователь возвращается на страницу списка заметок.

## Редактирование заметки

На странице `/edit/:id` frontend загружает заметку через `GET /notes/:id`.

Если backend возвращает `400` или `404`, форма не показывается, а пользователь видит сообщение о том, что заметка не найдена, и действие возврата к списку.

После успешного сохранения через `PATCH /notes/:id` пользователь возвращается на страницу списка.

## Удаление заметки

Удаление доступно:

- со страницы списка;
- со страницы редактирования.

Перед удалением frontend показывает стандартное браузерное подтверждение `confirm`. Пока идет удаление одной заметки, повторное удаление блокируется.

После удаления:

- на странице списка текущий список перезагружается с активными фильтрами;
- на странице редактирования пользователь возвращается на `/`.

## Обработка ошибок

Frontend разделяет несколько типов ошибок:

- frontend-валидация формы;
- HTTP-ошибки backend;
- сетевые ошибки до получения HTTP-ответа.

Ошибки frontend-валидации показываются рядом с соответствующими полями формы.

Ошибки backend показываются общим сообщением. Frontend не строит логику на точном тексте backend-сообщения и не пытается переводить его.

Если `fetch` не получает HTTP-ответ, например backend недоступен, frontend показывает общее сообщение о невозможности подключиться к серверу.

## Работа с `204 No Content`

При успешном удалении backend возвращает `204 No Content`. Такой ответ не содержит JSON-тела, поэтому frontend не вызывает `response.json()` для статуса `204`.

Это важное техническое правило API-слоя: обработка успешных ответов с телом и успешных ответов без тела различается.

## Горячие клавиши

Форма поддерживает сохранение через:

```text
Ctrl+Enter
```

Дополнительно страницы создания и редактирования защищены от двойной отправки формы. Это важно, потому что быстрая повторная отправка через клавиатуру может произойти до того, как кнопка визуально перейдет в disabled-состояние.

## UI/UX решения

Интерфейс спроектирован как минималистичная рабочая система, а не как демонстрационная landing page. Основной экран сразу показывает список заметок, фильтры и действия пользователя.

Ключевые UI/UX решения:

- темная тема спокойных тонов;
- компактная верхняя навигация;
- отдельные страницы создания и редактирования;
- карточки заметок с preview;
- счетчик найденных заметок;
- разные пустые состояния для отсутствия заметок и отсутствия результатов фильтра;
- кнопка сброса фильтров;
- визуальное выделение тегов;
- блокировка действий во время сохранения или удаления;
- сообщения об ошибках в контексте страницы или формы.

## Темная тема

Интерфейс использует темную тему, близкую по настроению к стандартной теме VS Code: не абсолютно черную, а основанную на мягких темных оттенках. Такой подход снижает визуальную нагрузку и делает приложение удобным для длительной работы с текстом.

Акценты используются ограниченно: для кнопок, активных пунктов меню, тегов и важных состояний.

## Цвета тегов

Цвет тега выбирается детерминированно по содержимому тега. Это означает, что один и тот же тег получает один и тот же CSS-класс цвета при каждом рендере.

Такой подход делает интерфейс визуально стабильным: пользователь начинает ассоциировать конкретный тег с конкретным цветом, но при этом frontend не хранит отдельную таблицу цветов.

## Accessibility

В интерфейсе используются базовые приемы доступности:

- `label` связан с соответствующим полем формы;
- для ошибок формы используются `aria-invalid` и `aria-describedby`;
- навигация имеет `aria-label`;
- списки тегов имеют текстовое описание через `aria-label`;
- кнопки блокируются через `disabled` во время выполнения операций.

Проект не претендует на полную WCAG-сертификацию, но базовая семантика интерфейса соблюдается.

## Переменные окружения

Минимальный `.env` для локального запуска:

```env
VITE_API_BASE_URL=http://localhost:3000/api/v1
```

Для production-сборки используется `.env.production`:

```env
VITE_API_BASE_URL=/api/v1
```

Относительный URL удобен при развертывании за nginx: frontend и API остаются на одном публичном origin, а конкретный внутренний порт backend скрыт за reverse proxy. При изменении версии API или адреса backend достаточно изменить переменную окружения.

```bash
npm run dev
```

После запуска Vite покажет локальный адрес приложения, например:


Production-сборка:

```bash
npm run build
```

Результат сборки создается в папке `dist`.

Перед сборкой Vite автоматически учитывает `.env.production`, поэтому production-версия не должна собираться с локальным `http://localhost:3000/api/v1`.

## Preview production-сборки

```bash
npm run preview
```

Команда позволяет локально проверить собранную production-версию приложения.

## Связь с backend

Для полноценной работы frontend требуется запущенный backend `notes-api`.

Локальная схема запуска:

1. Запустить MySQL.
2. Настроить и запустить backend.
3. Указать во frontend `.env`:

```env
VITE_API_BASE_URL=http://localhost:3000/api/v1
```

4. Запустить frontend через `npm run dev`.

Если backend недоступен, frontend запустится, но операции со списком заметок будут возвращать сетевую ошибку.

## Ручная проверка frontend

Минимальный сценарий проверки:

1. Открыть главную страницу.
2. Убедиться, что список заметок загружается.
3. Создать заметку с заголовком, текстом и тегами.
4. Проверить, что после создания происходит возврат к списку.
5. Убедиться, что теги отображаются в формате `#tag`.
6. Проверить поиск по слову из заголовка или текста.
7. Проверить фильтрацию по тегу.
8. Проверить комбинированный поиск: строка + тег.
9. Открыть редактирование заметки.
10. Изменить текст и теги.
11. Сохранить через кнопку.
12. Повторить сохранение через `Ctrl+Enter`.
13. Удалить заметку со страницы списка.
14. Удалить заметку со страницы редактирования.
15. Остановить backend и проверить отображение сетевой ошибки.

## Изначально заложенные ограничения

Текущая реализация системы сфокусирована на полном цикле работы с заметками: создание, чтение, редактирование, удаление, тегирование, поиск и взаимодействие с backend API. Поэтому часть возможностей, характерных для промышленных систем, сознательно не включалась в базовый объем проекта. Это позволило сохранить интерфейс и архитектуру понятными, контролируемыми и соответствующими объему проекта.

К основным ограничениям текущей версии относятся:

- **Однопользовательская модель работы.** В проекте не реализованы регистрация, авторизация и аутентификация пользователей. Все заметки рассматриваются как принадлежащие одному пользователю или одной рабочей области.
- **Отсутствие ролей и разграничения доступа.** Поскольку система является однопользовательской, в ней не вводились роли администратора, редактора или читателя, а также права доступа к отдельным заметкам.
- **Отсутствие пагинации.** Список заметок загружается целиком. Для текущего объема данных это упрощает интерфейс и не требует дополнительных состояний пагинации.
- **Один тег в фильтре.** Фильтрация реализована по одному тегу за раз. Multi-select по нескольким тегам не добавлялся, чтобы не усложнять UI и контракт API.
- **Простой поиск без морфологии.** Поиск выполняется как регистронезависимый поиск по подстроке. Морфологический поиск, исправление опечаток, полнотекстовые индексы и ранжирование результатов не реализованы, поскольку это отдельная поисковая подсистема, выходящая за рамки базовой CRUD-системы.
- **Отсутствие offline-режима и localStorage.** Данные не сохраняются в браузере через `localStorage`. Постоянное хранение вынесено на backend и реализовано через MySQL, что соответствует выбранной full-stack архитектуре.
- **Отсутствие загрузки файлов и изображений.** Система работает только с текстовыми заметками и тегами. Вложения не включались, так как потребовали бы отдельной модели хранения файлов, настройки загрузки, валидации типов и ограничения размера.
- **Нет отдельного API для управления тегами.** Теги вводятся пользователем в форме, включаются в `content`, извлекаются backend-слоем и возвращаются в составе модели заметки. Отдельный интерфейс управления тегами не реализован.
- **Простая обработка параллельных запросов.** Frontend защищен от двойной отправки формы и повторного удаления до завершения текущего запроса. При этом отмена устаревших поисковых запросов через `AbortController` не реализована, так как поиск применяется вручную по Enter или кнопке "Найти", а не на каждое нажатие клавиши.

Эти ограничения фиксируют изначально выбранные границы проекта и отделяют базовую систему заметок от более сложной промышленной платформы.

## Изначально заложенная расширяемость

Несмотря на сознательное ограничение функциональности, frontend изначально спроектирован как часть расширяемой системы. Он не привязан жестко к конкретному серверу, версии API или способу дальнейшего развития backend.

К ключевым решениям, обеспечивающим расширяемость, относятся:

- **Конфигурируемый базовый URL API.** Frontend использует переменную окружения `VITE_API_BASE_URL`, поэтому адрес и версия API не зашиты в компоненты приложения. При переходе на новую версию API достаточно изменить конфигурацию окружения.
- **Работа через REST API.** Frontend не обращается к базе данных напрямую и не хранит постоянные данные локально. Он взаимодействует только с backend API, что сохраняет разделение ответственности.
- **Разделение frontend и backend.** Frontend и backend находятся в отдельных репозиториях, но разрабатываются в рамках одного рабочего пространства. Текущий frontend является одним из возможных клиентов backend; при необходимости его можно заменить или дополнить другим клиентом без изменения backend-логики.
- **Компонентная архитектура.** Интерфейс разделен на страницы и переиспользуемые компоненты. Это упрощает добавление новых экранов и изменение существующих сценариев.
- **Выделенный API-слой.** Все HTTP-запросы находятся в `src/api/notesApi.js`. При изменении API-контракта основная часть адаптации будет сосредоточена в одном месте.
- **Выделенные утилиты работы с тегами.** Нормализация тегов, формирование `content`, обратная раскладка заметки и preview вынесены в `src/utils/notes.js`. Это упрощает тестирование и повторное использование логики.
- **Маршрутизация через React Router.** Приложение уже разделено на самостоятельные маршруты, поэтому его можно развивать новыми страницами без изменения базовой структуры.

## Возможные направления развития

В дальнейшем frontend можно расширить следующими возможностями:

- авторизация и личный кабинет пользователя;
- страницы профиля и настроек;
- пагинация или бесконечная прокрутка списка;
- фильтрация по нескольким тегам;
- отдельная страница управления тегами;
- markdown-редактор;
- загрузка изображений и файлов;
- autosave черновика;
- сохранение фильтров в URL;
- offline-режим;
- toast-уведомления;
- более развитая accessibility-проверка;
- автоматические frontend-тесты.

## Краткий итог

`notes-web` реализует самостоятельный frontend-модуль системы заметок. Он предоставляет пользовательский интерфейс для работы с заметками и тегами, взаимодействует с backend через REST API, поддерживает маршруты, формы, поиск, фильтрацию, обработку ошибок и темную визуальную тему. Архитектура остается достаточно простой для текущего проектного контекста, но содержит решения, которые позволяют развивать интерфейс и подключать его к будущим версиям backend API.
